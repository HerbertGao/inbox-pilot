## 需求
### 需求:P0/P4 即时推送
`shouldNotifyNow` 为 true（即最终优先级 P0/P4）时通知器必须**尝试**推送（成功→对应 `notify` 动作记 `done`；单次 `executeActions` 调用内重试耗尽仍失败→记 `failed`；无渠道→记 `skipped`），**不保证一定送达**（at-most-once-after-retry，见 executeActions / processing-pipeline）；`shouldNotifyNow` 为 false 时**禁止**推送。

#### 场景:P0/P4 触发推送
- **当** 一封 `FinalDecision.shouldNotifyNow` 为 true 的邮件
- **那么** 通知器必须**尝试**经渠道推送通知——每次 `processEmail` 调用至多一条；推送可能因失败（`failed`）或无渠道（`skipped`）而未送达，不阻断 `markProcessed`；跨崩溃重跑为 at-least-once（≤1 次重复），与流水线 at-least-once 一致

#### 场景:非即时优先级不推送
- **当** 一封 `shouldNotifyNow` 为 false 的邮件（如 P1/P2/P3）
- **那么** 通知器必须不推送（其去向是摘要/计数，属后续阶段）

### 需求:通知不泄露完整正文
通知内容必须只包含白名单结构字段——**来源邮箱标签**、主题、发件人、原因、**中文分类**、置信度,**禁止**包含完整正文（`textBody`/`htmlBody`,类型层排除不变）。

**来源邮箱标签**:渲染时优先用账号 `label`（中文别名,见 account-registry「账号可选展示别名 label」），未设则用账号 `email`（稳定必有）——二者经 `accountLabel` 投影到 payload。`accountId` 亦投影,仅作穿透链漏填时的**末位兜底**（裸 id、**绝不**渲染空来源）。**不**用 accountId-strip 作主回落（自定义 account-id 未必含邮箱、prefix-only id strip 后为空）。多账号下通知必须可辨来源。

**渲染净化（单点防御,choke point）**:**每个攻击者可影响的渲染自由文本字段**(主题 / 原因 / 发件人 / 风险标记 / 来源标签候选)在**渲染边界**必须净化——剥除 `\p{Cc}`(含 `\r`/`\n`) / `\p{Cf}` / U+2028 / U+2029 / U+2066–U+2069。**理由**:仅净化来源标签不够——subject 等含换行会在多行消息里**伪造结构行**(如假「邮箱：」行)、绕过来源可辨保证;且账号 `email`(IMAP `--email` 未按 denylist 校验、原样存)会经其重开 RTL-override 伪装面。来源标签按 **sanitize-then-fallback**:`label`/`email` 候选经净化,净化后为空才回落**裸 `accountId`**——后者是 **clean-by-invariant**(PK 已严格 ASCII、不含任何被净化字符),作末位非空兜底、**非**主动再净化(若未来放松 PK 字符集须把 accountId 也纳入主动净化)。

**中文分类**:category 英文枚举经**单点映射**渲染为**中文** hashtag（映射覆盖全部 category 枚举臂；新增枚举臂无映射必须构建期失败），如 `#系统告警`/`#交易`/`#安全`/`#营销`；**禁止**直接渲染英文枚举名。

**单一模板**:P0 与 P4 必须共用同一字段模板（消除现两分支字段分歧）；`riskFlags` **非空才**渲染风险行；**仅 P4** 附「不要点击链接、请直接进官网/客户端核验」类安全提示。label / 邮箱标签 / 分类均为结构字段,不引入正文。

#### 场景:通知指明来源邮箱（未设 label）
- **当** 推送任一通知、且其账号未设 `label`
- **那么** 通知必须含账号 `email` 作来源标签；**禁止**不显示来源 / 渲染空字符串（穿透链漏填时末位回落裸 `accountId`、仍非空）

#### 场景:来源标签渲染前净化（防 email 携注入字符）
- **当** 账号 `email`（或任何来源字段）含 `\p{Cc}` / `\p{Cf}` / bidi / 行分隔字符（如经未校验的 IMAP `--email` 注入 RTL-override U+202E）
- **那么** 渲染的来源标签必须已剥除这些字符;**禁止**未净化的 email 直接进通知行（防经未校验的 `--email` 做来源伪装）
- **且** 净化须在 fallback **之前**(先净化候选、净化后为空才回落):若来源标签净化后为空（如全 bidi/控制字符的 email），必须回落非空 `accountId`（ASCII、净化 no-op）——**绝不渲染空来源**;**禁止**把净化包在整个 fallback 外层（否则全危险字符的候选 pre-sanitize 非空被选中、再净化成空 → 空来源）

#### 场景:中文别名优先
- **当** 账号设了 `label`（如「公司邮箱」）并推送其一封通知
- **那么** 来源标签必须渲染该 `label`，而非派生标签

#### 场景:分类渲染中文
- **当** 推送任意 category 的通知
- **那么** 必须渲染对应**中文** hashtag；**禁止**渲染英文枚举名（如 `system_alert`）

#### 场景:P0/P4 单一模板、风险行条件显示
- **当** 推送 P0 或 P4 通知
- **那么** 必须用同一字段模板；`riskFlags` 为空时**不**渲染风险行、非空才渲染；**仅** P4 附安全核验提示

#### 场景:不含完整正文（不变）
- **当** 推送任意通知
- **那么** 通知 payload 与渲染文本**禁止**含 `textBody`/`htmlBody` 完整正文

### 需求:仅推送通知，绝不发送邮件
通知必须只发往聊天/推送渠道（telegram/bark 等），**禁止**触发任何邮件发送或回复（不可违反的硬约束）。

#### 场景:通知不触发邮件
- **当** 通知器推送任意通知
- **那么** 必须只调用聊天/推送渠道，禁止调用任何邮件发送 API

### 需求:渠道缺失时降级不崩
通知渠道未配置（如 `TELEGRAM_*` 缺失）时，通知器必须**降级为记日志并跳过**，禁止抛出未捕获异常或阻断处理流水线；降级时对应 `notify` 动作状态必须记为 `skipped`（区别于 `done`/`failed`）并含原因。

#### 场景:无渠道配置时降级
- **当** 需要推送但没有任何渠道凭据
- **那么** 通知器必须记一条结构化日志并跳过推送，不抛异常、不阻断 `processEmail`，且对应 `notify` 动作记为 `skipped`

### 需求:通知密钥只从配置读、不入日志
通知渠道凭据（本期 `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`）必须只从 P0 `config`（环境变量）读取，**禁止**写死在代码中；推送失败的日志**禁止**写入渠道凭据或邮件完整正文。

#### 场景:失败日志不泄露凭据与正文
- **当** 推送失败需记日志
- **那么** 日志必须只含结构化字段（如 kind/status/优先级），禁止含渠道凭据或完整正文
