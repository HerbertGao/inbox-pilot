# daily-digest 规范

## 目的
待定 - 由归档变更 daily-digest 创建。归档后请更新目的。
## 需求
### 需求:每日定点构建并推送摘要
系统必须在 `DIGEST_TIMES` 配置的每个时刻（默认 `12:30`、`21:30`）触发一次摘要：查出**自上次摘要以来尚未进过摘要**
的已处理邮件，组装文案，经既有通知渠道推送。当本次**既无 P1/P2 邮件、P3 计数又为 0**（含查到行但按优先级过滤后为空）时，
**禁止**推送空摘要（记 `kind:'digest-empty'` 日志即可）；只要有 P1/P2 条目**或** P3 计数 > 0 即推送。摘要使用邮件经
规则引擎裁定后的**最终优先级**（`mail_classifications.priority`），**禁止**依据 LLM 原始建议。纳入范围**不得**带邮件年龄
上限——只要 `processedAt != null` 且未进过摘要即可入，使停机期间积压的旧邮件不被永久排除。

#### 场景:到点触发并推送
- **当** 到达某个 `DIGEST_TIMES` 时刻且存在 P1/P2 邮件或 P3 计数 > 0 的未进过摘要邮件
- **那么** 系统必须组装摘要并经通知渠道推送

#### 场景:无新邮件不推送
- **当** 到达某时刻但无 P1/P2 邮件且 P3 计数为 0
- **那么** 系统**禁止**推送（不发空摘要）；记一条结构化日志

#### 场景:停机超过一天的积压邮件仍入摘要
- **当** 进程停机超过 24 小时后恢复，期间有未进过摘要的已处理邮件
- **那么** 这些邮件必须仍被纳入下一次摘要（**禁止**因年龄被永久排除）

### 需求:候选邮件按确定性顺序，标识用行主键
候选邮件必须用**确定性排序**返回：优先级档（P1 < P2 < P3）、同档按 `receivedAt` 升序、再按 `id` 升序——使分段边界
跨重复 build 稳定。候选与去重标识必须是 **`MailMessage.id`（行主键，repo 中称 `messageRowId`）**，**禁止**误用
`MailMessage.messageId`（可选的 RFC 头）——后者非 FK 目标，会破坏 `digest_items` 外键与去重。

#### 场景:候选排序稳定
- **当** 同一批候选被重复 build
- **那么** 排序必须一致（优先级档 / receivedAt / id），分段边界稳定

#### 场景:标识用行主键而非 RFC 头
- **当** 落 `digest_items` 或判定去重
- **那么** 必须用 `MailMessage.id`，**禁止**用 `MailMessage.messageId`（RFC 头）

### 需求:摘要内容按优先级分层
摘要文案必须按优先级分层（§13.2）：**P1 逐条**、**P2 逐条**（各含 发件人 / 主题 / 原因），**P3 仅计数**（输出条数，
**禁止**断言其已被标记已读——markRead 可能未执行或失败，摘要不核验 `mail_actions`）。P3 计数语义为「**自上次摘要以来
新增的 P3 条数**」（增量）。P0/P4 不入摘要（出口是即时推送），候选过滤后**只保留** `priority ∈ {P1,P2,P3}`。

#### 场景:P1/P2 逐条
- **当** 摘要含 P1 或 P2 邮件
- **那么** 每封必须逐条列出其发件人、主题、裁定原因

#### 场景:P3 仅计数且不断言已读
- **当** 摘要含 P3 邮件
- **那么** 只输出 P3 增量条数、**不**逐条列出、**不**声称「已标记已读」

### 需求:摘要不泄露完整正文且绝不发送邮件
摘要候选查询必须用**显式 `select` 白名单**（`MailMessage`: id / subject / fromName / fromEmail / receivedAt；
嵌套 `classifications.select`: priority / category / reason——**priority 必含**，是 P1/P2 逐条 vs P3 计数的判据），
**禁止**用 `include`（会把整行 `MailMessage` 含 `bodyText` 拉进结果对象）。`DigestCandidate` 类型**不得**含
`bodyText`/`htmlBody` 字段。摘要投递**只调用推送通知渠道**（telegram），**绝不**调用任何邮件发送/回复 API。
凭据与正文**禁止**入日志（错误路径只记脱敏 kind/code，不记原始 error/收件人 PII/正文）。

#### 场景:候选查询显式 select 不含正文
- **当** `listDigestCandidates` 查询邮件
- **那么** 必须用显式 `select` 白名单、结果对象**不含** `bodyText`；有断言测试覆盖

#### 场景:只推送不发邮件
- **当** 摘要被投递
- **那么** 系统必须只经推送渠道发送、**绝不**调用邮件发送 API

#### 场景:缺分类行的已处理邮件被排除
- **当** 某邮件 `processedAt != null` 但无 `mail_classifications` 行
- **那么** 系统必须**排除**该邮件并记一条 **debug** 级日志，**禁止**崩溃、**禁止**每轮 error 刷屏

### 需求:文案按 UTF-16 上限分段、单行截断、逐段提交
单条推送渠道有长度上限（Telegram `sendMessage` 上限 **4096 个 UTF-16 code unit**）。摘要必须以 `text.length`
（UTF-16 单位，**禁止**用码点计数）度量，分段为每段 ≤ `SEGMENT_MAX`（如 4000，留余量）的多段，**按整条 P1/P2 行切**。
每条渲染行（`发件人 - 主题 - 原因`）必须对**发件人（fromName/fromEmail，均来自不可信邮件头、无长度上限）、主题、原因
每个字段各自截断**到字段级上限、保留分隔符、空字段填占位，并以**整行最终再截断到 `SEGMENT_MAX`** 兜底——保证**任何单行 <
`SEGMENT_MAX`**（**禁止**只截 subject/reason 漏掉超长发件人）。截断必须**代理对安全**（不裂出孤立高代理）。每段携带其所含
邮件的 `messageRowIds`。编排必须**逐段提交**：顺序发各段，**某段发送成功后立即** `markDigested` 该段的 `messageRowIds`；
遇首个非 sent（失败/skipped）即停止本轮（其后段不发、不 mark），下次重试。

#### 场景:超长摘要分段且逐段提交
- **当** 摘要文案超过单段上限
- **那么** 系统必须分多段、每段 ≤ 上限、顺序发送，且**每段发成功即 mark 该段邮件**（非全发完才 mark）

#### 场景:超长单行（含超长发件人）被截断不致永久失败
- **当** 某 P1/P2 邮件的发件人/主题/原因极长，单行可能超过段预算
- **那么** 系统必须对发件人/主题/原因各字段 + 整行截断使其 < 段预算，**禁止**产生不可分段的超限单条导致永久发送失败

### 需求:同封邮件不重复进摘要
摘要去重必须经 `digest_items` 表的**存在性**落地：一封邮件只要有 ≥1 行 `(messageRowId, digestType)` 即必须被**排除**。
`digest_items` **无唯一约束**（本期不加，需迁移），重复行可能出现且**容忍**（读侧只看存在性）。**某段发送成功后才落该段
`digest_items`**——发送失败的段及其后段**禁止**落行，使其邮件在下次摘要被重新纳入（不因失败永久丢出摘要）。

#### 场景:已入摘要不重复
- **当** 某邮件已有 ≥1 行 `digest_items`
- **那么** 后续摘要必须排除该邮件

#### 场景:发送失败不丢件
- **当** 某段发送失败（含无渠道 skipped）
- **那么** 系统**禁止**为该段及其后段邮件落 `digest_items`；这些邮件在下次摘要被重新纳入

### 需求:DIGEST_TIMES 配置解析与降级
`DIGEST_TIMES` 必须区分「env 缺省」与「显式空串」：**缺省（未设）→ 默认 `12:30,21:30`；显式空串 → 不调度**。
config 层必须用**裸 `z.string().optional()`**，**禁止** `z.preprocess(emptyToUndefined, …)` 包裹或 zod `.default()`
（否则显式 `''` 被归一/复活成默认排程）。每个 token 解析为两整数时刻（接受 `9:5` 与 `09:05`，范围 `0–23`:`0–59`），
非法项（空/越界/非两段数字）必须**在 `cron.schedule` 之前**记错并跳过、不中断其余、不把非法表达式交给 node-cron。
合法时刻必须**按规范化 `M H` 去重**（`12:30,12:30` 只起一个任务，否则同分钟两任务重复推送 + 重复落行）。
全空/全非法 → 不调度，但服务必须正常启动（/health 可用）。

#### 场景:多个合法时刻各起一调度
- **当** `DIGEST_TIMES=12:30,21:30`
- **那么** 系统必须为 12:30 与 21:30 各起一个每日触发

#### 场景:重复时刻去重
- **当** `DIGEST_TIMES=12:30,12:30`
- **那么** 系统必须去重、只起一个 12:30 任务（不重复推送、不重复落行）

#### 场景:显式空串不调度（区别于缺省走默认）
- **当** `DIGEST_TIMES=`（显式空串）
- **那么** 系统**不调度**任何摘要；而 env 完全缺省时则用默认 `12:30,21:30`

#### 场景:非法项调度前跳过不中断
- **当** `DIGEST_TIMES` 含非法项（如 `25:00` / `abc` / 尾逗号空 token）
- **那么** 系统必须在 `cron.schedule` 之前跳过该项并记错，其余合法时刻正常调度、不抛非法 cron 表达式

#### 场景:全空/全非法不调度但服务正常启动
- **当** `DIGEST_TIMES` 为空或全部非法
- **那么** 系统不调度任何摘要、服务照常启动、/health 可用

### 需求:摘要调度跨任务互斥、错误隔离、时区与构造期安全
多时刻是多任务，互斥**不得**依赖 node-cron `noOverlap`（仅单任务内不重入、跨不了任务）。系统必须用**一个进程内共享
`digestRunning` 锁**（所有 digest 任务共用）：回调顶端**同步** `if (digestRunning) return; digestRunning = true;`
（先于首个 `await`），**`finally` 释放**——防相邻/重复时刻或慢 digest 跨任务并发推送与重复落行。`timezone` 显式传入
（容器 `TZ` 兜底，代码层可见可测）。**每个 `cron.schedule(...)` 的构造须各自 try/catch**：非法 `timezone`/表达式在构造期
**同步抛**（在运行期回调 try/catch 之外），必须被接住 → 记脱敏 kind、跳过该任务、**保轮询 + /health 存活**，**禁止**拖垮整个服务。
摘要的 cron 回调体必须 `try/catch/finally`：捕获 build/repo/send 错误、记**脱敏**日志（只 kind/code，**禁含**原始
error/cause/正文/收件人 PII/凭据）、`finally` 释放锁、**绝不**让 rejected promise 漏出回调。

#### 场景:跨任务互斥（相邻/慢 digest 不并发）
- **当** 配了相邻时刻（如 `12:30,12:31`）或某次 digest 多段发送跨过下一触发
- **那么** 共享 `digestRunning` 锁必须使后到的触发跳过（不并发执行摘要、不重复推送/落行）

#### 场景:非法时区不拖垮服务
- **当** `TZ`/`timezone` 为非法（非 IANA）串，致 `cron.schedule` 构造期抛错
- **那么** 该任务构造的 try/catch 必须接住、记脱敏 kind、跳过该 digest 任务，轮询与 /health 仍正常

#### 场景:运行期错误被隔离不崩进程
- **当** 摘要一轮中 build/repo/send 抛错
- **那么** 回调必须 catch 并记脱敏日志、`finally` 释放锁、不崩进程、不泄露原始错误/PII/凭据

### 需求:优雅关闭停止摘要调度
摘要调度产出的 cron task 必须与轮询 task 进入 main **同一个被 `shutdown()` 迭代的 task 列表**，收到关闭信号
（SIGTERM/SIGINT）时一并停止——**禁止**放进未被 `shutdown()` 迭代的独立变量。

#### 场景:关闭停止摘要 task
- **当** 进程收到 SIGTERM/SIGINT
- **那么** 系统必须停止所有摘要 cron task（与轮询 task 同列表）
