- [x] 1.0 `src/actions/actionTypes.ts`：**扩展 `ActionStatus` 联合类型 + const 对象**新增 `'retrying'`、`'dead_letter'`（现为 `'pending'|'done'|'failed'|'skipped'`）——否则 `enqueueRetry`/`markActionDeadLetter` 写入这两值、`selectDueRetries` 按 `'retrying'` 过滤、`updateAction(status: Exclude<ActionStatus,'pending'>)` 均无法 typecheck，6.1 的 `tsc --noEmit` 必失败。（本文件须列入 proposal「影响/修改」。）
- [x] 1.1 `prisma/schema.prisma`：`MailAction` 新增 `retryCount Int @default(0)`、`nextRetryAt DateTime?`；status 仍自由 String（新增取值 `retrying`/`dead_letter`，无 enum）。**同一迁移加索引（必须）**：① `mail_actions` 对 `(messageId, actionType)` 的 **partial unique index `WHERE status IN ('pending','retrying')`**（活跃行唯一性，决策 4；Prisma schema 无法表达 partial，经迁移 raw SQL）；② `mail_actions(status, nextRetryAt)` drain 查询索引（优先 partial `WHERE status='retrying'`，决策 6）；③ `mail_classifications(messageId, createdAt desc)`（重建"最新分类"，FK 现无索引）。`prisma migrate dev` 生成迁移（列为元数据级、无重写；既有行兼容：retryCount=0、nextRetryAt=null、旧 status 不动；表已大时索引用 `CREATE INDEX CONCURRENTLY` 独立非事务迁移）。
- [x] 1.2 `src/repo/mailRepo.ts`：新增 `selectDueRetries(accountId, now, limit)` —— **先选 retry 动作行**（`status='retrying' ∧ nextRetryAt ≤ now ∧ message.accountId=accountId`，按 nextRetryAt 升序、limit=`DRAIN_BATCH_CAP`），**再以 LEFT join / 单独 fetch 取重建输入**（mail_messages 行 + 最新 mail_classifications 行，用 `[{createdAt:'desc'},{id:'desc'}] take 1`）。**禁用 INNER join 重建输入**——否则关联行缺失的 retry 动作会被 join 静默丢出选择集、永不被 drain、永不进永久死信（绕过 1.4 的"行缺失→永久"判别）；missing 关联行**必须**作为可识别的"缺失"返回值流到永久死信路径（注：`mail_messages` 受 `mail_actions→mail_messages` 的 Restrict FK 保护、不会缺失；`mail_classifications` 无 FK 保护，故尤须 LEFT join 不丢行）。依赖 1.1 的 `(status, nextRetryAt)` 索引（避免每 poll seq scan）。
- [x] 1.3 `src/repo/mailRepo.ts`：**`recordAction` 改为对 `(messageId, actionType)` 活跃行 upsert，按既有活跃态分流并返回处置信号**——命中活跃 **`retrying`** 行 → **保持 `retrying` 原样、不清零 `retryCount`/`nextRetryAt`**、返回"已在 durable 队列"信号（供 `executeActions` SKIP 内联执行）；命中活跃 **`pending`** 行（崩溃残留）→ 复用同行（信号"继续执行"）；无活跃行 → INSERT `pending`（信号"继续执行"）。配合 1.1 的活跃态 partial unique index 强制至多一条活跃行，使 re-poll 重跑既不产生第二条活跃行、也不清零 durable 进度。新增动作状态推进方法 `enqueueRetry(actionRowId, retryCount, nextRetryAt, error)`（落 `retrying`）、`markActionDeadLetter(actionRowId, error)`（落 `dead_letter`）；`updateAction('done')` 复用既有。
- [x] 1.4 `src/repo/mailRepo.ts`：新增重建读取 —— 从行重建 **action-input-sufficient 投影** `NormalizedEmail`（providerMessageId/messageId/threadId/uid/subject/fromEmail/fromName/bodyText/snippet/receivedAt/hasAttachments；**合成 `to:[]`、`headers:{}`**——库中无；`provider` 由 `MailAccount.provider` 派生）与 `FinalDecision`（priority/category/confidence/reason 列 + `rawAiJson.finalDecision` 块）；**多分类行取最新用 `orderBy [{createdAt:'desc'},{id:'desc'}] take 1`**（与 `listDigestCandidates` 一致，禁只按 createdAt——并列会改判）。**重建失败分两类返回可识别结果（判别机制显式）**：Prisma 行查询返回 null → 永久；`rawAiJson` 在**独立解析 `try`** 内 throw 或 `finalDecision` shape 校验失败 → 永久（供 drain 落 dead_letter）；**Prisma 行读取本身**抛 I/O 错误 → 瞬时（向上传播、保持 retrying，**不**落 dead_letter）。**禁**用包住整个重建的单一 try/catch 笼统归类。

## 2. executeActions 瞬时耗尽落 retrying

- [x] 2.1 `src/actions/executeActions.ts`：三动作（reflectPriority/markRead/notify）发送态瞬时**耗尽分支**由 `updateAction(failed)` 改为 `enqueueRetry(retryCount=0, nextRetryAt=now+backoff(0), 脱敏error)` 落 `retrying`（**仅发送态瞬时失败**；`ProviderReauthRequired`/repo-I/O 向上传播通道不变）。**每动作先看 `recordAction` 返回信号：若"已在 durable 队列"（命中活跃 `retrying` 行）→ SKIP 本轮内联执行**（交给 drain、保留 durable 进度），否则正常执行。notify `skipped`（无渠道）与 `done` 路径不变。
- [x] 2.2 抽出长程退避 `durableBackoffMs(n)` **精确值表**（不是约值）：`[60_000, 300_000, 1_800_000, 7_200_000, 21_600_000, 86_400_000]`（=1min/5min/30min/2h/6h/24h，索引 `n∈0..5`；24h 封顶）+ 常量 `MAX_DURABLE_ATTEMPTS=6`、`NOTIFY_STALENESS=24h`、`DRAIN_BATCH_CAP=50`、`DRAIN_TIME_BUDGET_MS`（软 deadline、保守分额自 `DEFAULT_POLL_TIMEOUT_MS`）（集中一处、可调）。**推进顺序固定**：drain 失败 → `retryCount += 1` → **先判 `retryCount ≥ MAX(6)` → 死信（不再索引 backoff）**；否则 `nextRetryAt = now + durableBackoffMs(retryCount)`（此时 `retryCount∈1..5`，合法索引）。初次入队用 `durableBackoffMs(0)`。
- [x] 2.3 测试：三动作瞬时耗尽落 `retrying`（retryCount=0 + nextRetryAt 落库）、不落 failed；reauth 仍 failed+re-throw 不入 retrying；skipped/done 不变。**活跃行唯一性 + 进度不清零**：reflectPriority 落 `retrying`（retryCount=3）后同邮件同 actionType 再 `recordAction`（模拟 re-poll 重跑）**命中同一行、保持 `retrying`、retryCount 仍 3、executeActions SKIP 内联执行**（断言 partial unique index + upsert + skip 信号、不新建第二条活跃行、不清零进度）。

## 3. retryQueue：drain 单动作重试 + 状态推进 + 死信 + staleness

- [x] 3.1 `src/actions/retryQueue.ts`：`drainAccountRetries(accountId, { provider, notifier, repo, clock, deadline })` —— deps **必须含 `notifier`**（重试 notify 动作、账号无关）与软 `deadline`（决策 6）。`selectDueRetries` → 逐条（try/catch 隔离）重建输入（1.4）→ 按 actionType 复发原动作（ReflectPriority→provider.reflectPriority / MarkRead→provider.markRead / Notify→notifier.notify，**复用已存 FinalDecision、绝不重新 LLM 分类**）。每条前检查软 deadline，超预算即停止本轮（剩余下轮）。
- [x] 3.2 单条结果推进：成功→`done`；**普通瞬时失败**→`retryCount += 1`、`nextRetryAt=now+durableBackoff(retryCount)`、保持 `retrying`（**不轮内 sleep**）；**增量后 `retryCount ≥ MAX_DURABLE_ATTEMPTS`（=6，统一表述，非 `+1≥`）**→`dead_letter`；notify 且 `receivedAt` 超 `NOTIFY_STALENESS`→直接 `dead_letter` 不补发（markRead/reflectPriority 无 staleness 上界）；**永久重建失败（行缺失/JSON 损坏）→`dead_letter`；瞬时 DB I/O 错误→保持 `retrying`、不推进 retryCount、向上传播（不死信）**；`ProviderReauthRequired`→**逐条 catch 必须重新抛出它**（不被隔离吞掉）→停止本账号本轮 drain、当前行保持 retrying 不推进不进死信、向上传播账号级失败。
- [x] 3.3 死信可观测：进 `dead_letter` 记脱敏结构化日志（kind+actionType+retryCount，**绝不**正文/凭据/PII）；drain 自身有界（条数 ≤`DRAIN_BATCH_CAP` **且** 软 deadline 提前退出）、逐条隔离普通异常不互相阻断、但 reauth 穿透隔离停整轮。
- [x] 3.4 测试（注入假 provider/notifier/时钟/repo/deadline）：到期项被重试至 `done`；持续失败按长程退避推进 retryCount 直至 `dead_letter`（恰好 6 次、retryCount 达 6）；超 staleness 的 notify 直接 dead_letter 不补发；markRead 过 24h 仍重试不进死信；**永久重建失败→dead_letter 不崩；瞬时 DB 错误→保持 retrying 不死信不推进 retryCount**；**reauth（第 k 条）→重新抛出停整轮、其后未试行不动、行保持 retrying**；普通瞬时异常逐条隔离不停整轮；drain 有界（>cap 只处理 cap；超软 deadline 提前退出、剩余下轮）。
