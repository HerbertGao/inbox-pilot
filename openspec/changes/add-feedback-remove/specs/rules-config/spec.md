## 新增需求

### 需求:noise overlay 的机器写入语义——canonical 归一、合法性、集合运算与原子发布

`noise_senders.overlay` 是**机器文件**（loader 只读、一行一个发件人），其**唯一写者**是 `apply-feedback` 路径。该路径**禁止**写人工维护的 `rules.yaml`——两者的合并只发生在加载期。

**overlay-only 语义（必须写进面向读者的文档）**：生效降噪集是 `rules.yaml noise_senders ∪ overlay`，本路径**只动 overlay**。因此同时被人工 `rules.yaml` 命中的地址被「移出」后**仍会被降噪**，「不在名单」也只表示**不在机器 overlay**。**人工规则要人工改**——**禁止**让读者以为移出是全局撤销。

**两个归一，对应两个不同的问题**（各只有一份实现，都住 loader 模块）：

- **「一行是什么」** = `trim` → 转小写 → 丢空。**刻意不剥 `<>`**，与本能力生效前逐字节同语义——存量 overlay 的生效降噪集**不因本能力发生迁移**（不存在「惰性行转活、开始静默已读」这类无回执的变更）。它是**幂等**的。
- **「用户指的是哪个条目」** = `trim` → 剥掉**所有**包裹层 `<>` → 转小写。`<>` 剥到不动点（**不是只剥一层**：只剥一层会产出仍带 `<>` 的值，那个值既不是合法的行、又会被写盘，形成「读→写不是不动点」的漂移，一次无关的写就能把惰性行推向激活）。其输出必为上一条的不动点。

**写路径只做收与拒，禁止做改写**：除上述两步（它们把同一个条目的书写变体折成一个，不改变它指谁）之外，**禁止**再加任何「替用户猜他想要哪个地址」的变换——每多一条，写进文件的条目就与用户提交的条目多一处不等，而用户在确认页看到的是后者。`mailto:` 前缀因此走**拒绝**（见可加入判据的豁免⑤），**禁止**走剥离。

**方向决定用哪一个**：`add` 问「你指哪个地址」（剥 `<>`）；`remove` 问「你要删哪一行」（不剥——存量行可能就长成 `<x@y>`，剥了就对不上文件里那一行）。

**合法性分两组，必须分开读**：第一组是**共用前置**（「这是不是一行合法的 overlay 行」），`add` 与 `remove` 都要过；第二组是**可加入判据**（「这一行准不准被加进来」），**只**约束 `add`。两组的边界直接决定存量条目能不能被撤销——把任一格从第二组挪进第一组，就会让对应的一整类存量行结构性不可移除。

**第一组——是不是一行合法的 overlay 行（共用前置，两个方向都要过）**：

| 项 | 规则 |
|---|---|
| 类型 | 非 `string` → 非法 |
| 已归一 | **必须**是「一行是什么」那份归一的**不动点**（等价于：无首尾空白、全小写、非空——归一后长度为 0 的串不是不动点） |

**第二组——是不是可加入（只约束 `add`）**：

| 项 | 规则 |
|---|---|
| 控制字符 | 含任一 ASCII 控制字符 → 非法。正则**必须用码位转义写**（`\u0000-\u001f`、`\u007f`）；**禁止**把控制字符本身写进源码或文档——它在编辑器 / 剪贴板 / JSON 往返里会被静默吃掉，一份「看起来有这个字符类」的正则会变成没有 |
| 非 ASCII | 含任何码位 > `U+007F` 的字符 → 非法 |
| 长度 | > **254** 字符 → 非法（RFC 5321 的地址上限即 254） |
| `mailto:` 前缀 | 以 `mailto:`（大小写不敏感）开头 → 非法。**拒绝，不剥离** |
| 域名条目（无 `@`） | 全串在匹配侧域名归一的字母表 `[a-z0-9.-]` 内，**且必须含 `.`** |
| mailbox 条目 | `local@domain`：`local` 在匹配侧的 `[^\s<>@]` 内且非空；`domain` 在 `[a-z0-9.-]` 内且非空 |

**非 ASCII 与控制字符这两条在归一「之前」判，是本表仅有的例外，且是刻意的**：Unicode 小写会把 `K`（U+212A KELVIN）折成 ASCII `k`，归一后再查就查不出来——用户输入的 `K.com` 会静默变成一条针对 `k.com` 的**域级**规则。其余各项在归一后判。

**可加入判据 =（匹配侧可达集 − 五项政策豁免）∩「长度 ≤ 254」。本文件是这条规则的唯一权威出处，其余文档只引用、不复述。**

**禁止把它写成一个裸等式**：长度上限是写入侧的资源闸，不是从匹配侧减出来的政策格（匹配侧对 255 字符的地址照样命中），故它是第六处偏离、形态与前五项不同。写成等式会让性质测试要么漏掉这一处、要么把它冒充成一条政策豁免。

底座（可达集）由匹配侧的两条谓词两端锚定得到：地址走 `normalizeFromAddress` 的 `^[^\s<>@]+@[a-z0-9.-]+`，域名走 `normalizeFromDomain` 的 `[a-z0-9.-]+` 后按等值或后缀比，故底座恰是那两条归一的**不动点判定**。

**宽于底座禁止**：放行 `<a@x.com>`、`a b@x.com`、`a@x_y.com` 会写进一条**永不命中**的规则 = false-green——与拒绝 IDN 是同一条理由。字母表判据同时保证 VERP/SRS（`bounces+1=user.com@x.net`、`srs0=a=b=user@fwd.net`）与 `ops!tag@x.com` 不被误拒。

**严于底座只允许经下表这五项豁免**——每一项都是政策裁决而非从匹配侧推导出的结论，且都已核实匹配侧确实命中：

| 豁免 | 例 | 匹配侧 | 减掉它的理由 |
|---|---|---|---|
| ① local part 含非 ASCII | `é@x.com` | **命中**——`[^\s<>@]` 收下每一个非 ASCII 字符 | 内容侧的不可信字节不得跨过写盘边界，且与「非 ASCII 域名（IDN）一律拒」同裁 |
| ② local part 含控制字符 | local 里带 U+0001 | **命中**——同上 | 同上；控制字节一旦进机器文件，就会在编辑器 / 日志 / 剪贴板往返里被静默吃掉 |
| ③ 无点的纯域名条目 | `nas`、`localhost`、`router` | **命中** | 爆炸半径：一条即静音整个后缀，比单个地址大一个量级 |
| ④ 裸 TLD | `com` | **命中** | 同上，而 `.com` 是其中最大的那个后缀 |
| ⑤ 前导 `mailto:` | `mailto:a@x.com` | **命中**——`:` 与 `m` 都在字母表内 | 带前缀的条目匹配侧**永不命中**，而把它改写成 `a@x.com` 是替用户解析意图、写路径的契约禁止（local part 真叫 `mailto` 的发件人会被改成另一个地址、静音错的人）。故**拒绝**，让调用方自己提交裸地址 |

非 ASCII **域名**不在此表内：匹配侧的域字母表是 `[a-z0-9.-]`，它本就不在可达集里，归「宽于底座禁止」那一条。

**无点域名那一格的代价必须写明，禁止只举裸 TLD**：它挡住的不只是 `com`，还有 `nas`、`localhost`、`router`——正是本能力在地址层面特意支持的那类内网主机（`root@nas` **必须**被接受）。故「把某台内网主机整机静音」这个形态本能力**不提供**，替代路径是**按地址加**（`root@nas`、`cron@nas` 各一条）。

**在这五项之外再严一格就是缺陷**，且是本能力实测到的一处功能回归：按 RFC dot-atom + 域标签 ≤63 + 纯字母 TLD 判时，`root@nas`（无点域）、`admin@10.0.0.5`（数字 TLD）这一整类——NAS、路由器、内网 cron——在匹配侧**本来就命中**，却被判为不可加入；而它们正出现在摘要的高频发件人表头、被展示为可加入。**判据超出豁免表再收紧，就等于把真实存在的发件人锁在反馈闭环之外。**

**非 ASCII（IDN）条目必须拒绝，禁止单侧归一**：匹配侧比对的是 normalizer 产出的 `fromEmail`（**只小写、不转 punycode**），故只在写入侧做 IDN 归一会写进一个**永不命中**的条目 = false-green。支持 IDN 必须写入侧与匹配侧同时改，并含存量 overlay 迁移，不在本能力范围。

**入口的失败语义方向相反，必须分开**：

- **提案腿（干跑）对非法项禁止抛错**：非法项的结果是**它不出现在提案里**，一项都没有时两侧皆空数组。上层的健康态由最近一次 run 派生，一次打错字的失败会把健康的服务画成故障。
- **应用腿必须抛错**：非法项、**非 canonical 项**、同项冲突一律抛错。归一对合规输入是幂等的，**不幂等即说明调用方跳过了提案阶段**，是契约违规——这条让「确认页显示的 == 实际写入的」从纪律变成结构保证。

**`existing` 的定义**：`existing` 是**当前 overlay 文件的条目集**，**必须**经上述那一个行归一函数读出，**禁止**在其之上再叠任何一层。

**撤销可达性——本能力的核心不变量**：设 `L` = loader 接受的行语言，则**对 `L` 里的任意一行 `l`，请求 `{ remove: [l] }` 都必须被接受并真正删除它**，两条腿皆然。不满足它的后果是确定的：`remove` 够不着的行会永远留在 overlay 里静默已读，而契约禁止手改机器文件。

**这条按可达性陈述，禁止改写成谓词代数的推论**（如「共用前置里不含任何可加入分量，故 `L ⊆ W_remove`」）：闸门是逐道加进来的，那个论证每加一道就要重来一次，而它已被论错过两次——长度闸与请求字节闸都曾以「它不是可加入分量」为由放进共用前置，两次都让一整类存量行不可移除。按可达性写则落法唯一且可机械检查：**任何批量闸（条目数、请求字节，以及将来新增的任何一道）都必须对本次请求的第一条豁免，只从第二条起生效**。

`W_add ⊊ L`：`com` 属 `L` 而不属 `W_add`（政策豁免③④）——**加**得受判据管，**删**不受。

**读失败必须 fail-closed（与 loader 的 fail-open 方向相反，二者都对）**：**`statSync` 与 `readFileSync` 的失败都必须被捕获**（`throwIfNoEntry:false` 只压制文件不存在，权限/软链环照抛；而该读在模块加载期的调用链上，逃逸即整个模块 import 失败、服务起不来）。loader 读不到 overlay → 空集是正确的（读不到就不静音，安全方向）；但**写路径与提案腿禁止把「读不到」当「现有集为空」**——文件不存在（`ENOENT`）才是真的空集，其余读错误与「文件已超过 loader 上限」**必须**使应用腿抛错、拒绝据此改写名单。否则：add 侧会全量覆盖、静默抹掉整份名单并回绿；remove 侧会回执 `not_present`，而该地址其实还在名单里、还在被静默已读——用户以为已撤销，于是不会重试。提案腿不抛错，但读失败时**必须**给出空提案（两侧皆空）：此时它无从知道 diff，而提议一份应用腿必然拒绝的变更会让用户确认后拿到失败；事件契约只有两个字段、表达不了「overlay 不可用」。响亮失败由应用腿承担。

**overlay 的路径是派生的，禁止给它单独的旋钮**：路径**恒为** `dirname(rules.yaml)/noise_senders.overlay`。只有 `RULES_FILE` 一个旋钮决定这两个文件的位置，故它们**不可能被指到对方身上**——一个指错的 overlay 路径会把人工维护的 YAML 按平铺格式整体重写、缩进结构毁掉、无备份，而回执照报成功。

判断一个旋钮该不该存在，用同一条尺子：**它被设错时是响亮失败还是静默失败**。`RULES_FILE` 设错的后果是加载失败、全字段 carry-forward、一条告警——响亮，operator 看得见，故保留；单独的 overlay 路径旋钮设错的后果如上——静默，故它不存在。本项目**刻意保持低可配置度**，**禁止**把自己呈现成一个高度可配的系统。

**写侧闸门（三条，缺一即为已知可达的静默失效）**：① 序列化后的字节数 > loader 上限（`MAX_RULES_FILE_BYTES` = **256 KiB**，与 loader 共用同一个常量）→ **必须**抛错拒绝写入（写下去 loader 会**整份**忽略 overlay，等于所有降噪一次性失效，而 run 仍是绿的）；② 单侧条目数 > 上限（本能力取 500，**按去重前的入参数组长度**计）→ **必须**抛错；③ `rules.yaml` 自身被命名为 `noise_senders.overlay` → **必须**抛错拒绝写入（这一条撞名会让写 overlay 就是写 `rules.yaml`）。

**③ 是一次纯字符串比较**（`resolve()` 两边取等），**禁止**落任何文件系统调用：路径既然派生自同一个旋钮，两边只有在 rules 文件自己就叫 `noise_senders.overlay` 时才可能相等。「这两条路径是不是同一个文件」那一整类别名判定（软链 / 硬链 / 大小写不敏感盘 / bind mount）在此**没有作用面**，**禁止**为它引入任何机制。

**两侧的合规判据不同，且该差异只允许存在于一处**（一个按方向取参的共用谓词——写成两份必然只改得动一半）：`add` 项**必须**同时满足「是合法的行」与「可加入」；`remove` 项**只**要求「是合法的行」，**禁止**要求可加入——否则本能力生效前写入的存量条目会变得**结构性不可移除**，而契约禁止手改机器文件，撤销通道对最可能被误加的那批条目恰好失效。删除永远是安全方向。

**长度上限只在 `add` 侧**：`> 254` 字符的行 `remove` **必须**收得下。这类行**恰恰是产品自己写出来的**（本能力生效前的 `apply-feedback` 没有任何长度闸），把它挡在撤销通道外就是让产品自己制造的条目结构性不可移除，说它「只可能来自手改」是错的，靠手改捞出来更与下方「人工介入只允许在一种情形下发生」冲突。

`remove` 侧的无界问题由**请求字节闸**关掉：**单侧请求的序列化字节 > `MAX_REQUEST_BYTES`（64 KiB）时，应用腿必须抛错、提案腿必须截断**，两条腿、两个方向各判一次；**从第二条起才累计**（上文「撤销可达性」的落法），故一条任意长的存量行永远可以单独提交移除。不设它则任意长的串可进 `not_present` 回执与运行轨迹（500 项即可造出数百 MB 的事件）。

**集合运算与发布**：一次应用求 **`(existing ∪ add) \ remove`**，经**同盘 tmp + rename** 一次性原子发布（**禁止**分两次写）。tmp 文件名**必须**含进程标识（固定名会让并发写互踩，且可被预置为软链把写入引向别的文件），并以**不跟随软链**的方式创建。`added` = add 中不在现有集的，`already_present` = 已在的，`removed` = remove 中真在现有集的，`not_present` = 不在的。`added` 与 `removed` **皆空时禁止写文件**。同一 input 内 add / remove 各自**按归一后的值**去重。

**回执必须与请求配分**：`added ∪ already_present` **必须**等于去重归一后的 `add`、`removed ∪ not_present` **必须**等于去重归一后的 `remove`，**四桶两两不交**，且**禁止**含请求外的地址。

**同一项同时出现在 add 与 remove 必须抛错**：`(existing ∪ add) \ remove` 会让 remove 悄悄胜出，而回执 `{added:[X], removed:[X]}` 在读者眼里是「加了又移了」、文件里却没有 X——回执说谎。

**读失败与超限时的可修复性**：overlay 超过 loader 上限时应用腿抛错，故此状态下**增删皆不可行**；解除只能靠 operator 直接截断该机器文件（这是唯一允许人工介入的情形，须在文档中写明）。

**可逆性**：overlay 的字节内容**必须**是「有序条目集」的纯函数——条目集按行序维护（新增追加在末尾、删除不扰动其余行序），故**条目集相同 ⇒ 字节相同**。由此推出本能力的核心保证：对同一地址先 add 后 remove、**其间条目集无其它净变更**时，overlay 的字节内容回到 add 之前。

（措辞刻意用纯函数而非「先加后移必回原字节」：后者按字面可被 `add X → add Y → remove X` 证伪——文件此时是 `F+Y` 而非 `F`，而这正是设计想要的行为。）**字节等价只对由本路径写出的文件成立**；人工编辑过的存量文件（无尾换行 / CRLF / 空行 / 重复行 / 大写）写回时按 loader 的逐行归一重新序列化，**只保证集合等价**。

#### 场景:写入前 canonical 归一，且两个入口共用同一函数
- **当** 提案腿收到 `"  <FOO@Example.COM>  "`
- **那么** 提案里的条目**必须**是 `foo@example.com`；把该提案原样投给应用腿**必须**通过，且写入 overlay 的那一行**必须**与提案逐字相同

#### 场景:应用腿拒绝非 canonical 项
- **当** 未经归一的串（`"  <FOO@Example.COM>  "`、`"A@X.com"`、`" a@x.com"`）被直接投给应用腿
- **那么** **必须**抛错使 run 失败，且 overlay 的内容与 mtime **必须**均未变

#### 场景:应用腿拒绝非法项与畸形 input
- **当** 应用腿的 **`add` 侧**收到空串、`foo@`、`@b.com`、`a@@b.com`、无 `@` 无点的裸串（`nas`、`localhost`、`com`）、`<a@x.com>`、`mailto:a@x.com`、local 或 domain 出了匹配侧字母表（`a b@x.com`、`a@x_y.com`）、非 ASCII、含控制字符、超长、非字符串项；或**任一侧**的键存在但不是 `string[]`、条目数超上限、请求序列化字节超上限、含非归一项
- **那么** **必须**抛错，且 overlay **必须**未被写

#### 场景:内网主机与数字 TLD 必须可加入
- **当** 应用腿的 `add` 侧收到 `root@nas`（无点域）或 `admin@10.0.0.5`（数字 TLD）
- **那么** **必须**接受并写入——匹配侧对这两个形态本来就命中，且它们不在豁免表内；拒绝它们等于把 NAS / 路由器 / 内网 cron 这一整类真实发件人锁在反馈闭环之外，而它们正被摘要展示为可加入

#### 场景:缺 key 视作空数组，禁止抛错
- **当** 应用腿收到只含 `add` 而无 `remove` 键的 input
- **那么** **必须**正常应用，`removed`/`not_present` 为空数组；**禁止**把缺键当非法输入

#### 场景:提案腿对非法项不抛错
- **当** 提案腿收到含非法项、冲突项或畸形 shape 的 input
- **那么** run **必须**正常结束、**必须**无任何写，相应项**必须**不出现在提案的任一侧

#### 场景:同项冲突被拒
- **当** 同一项（归一后）同时出现在 `add` 与 `remove`
- **那么** 应用腿**必须**抛错、overlay **必须**未被写；提案腿**必须**把该项从两侧同时剔除

#### 场景:集合运算一次原子发布且回执配分
- **当** 一次应用同时含 add 与 remove
- **那么** **必须**求 `(existing ∪ add) \ remove` 后经 tmp+rename **一次**发布；回执四桶**必须**与请求配分、两两不交

#### 场景:重发同一应用幂等且不写
- **当** 对同一组 add/remove 重发应用
- **那么** `added`/`removed` **必须**退化为空、对应条目落 `already_present`/`not_present`，且 overlay **必须**未被写（mtime 不变）

#### 场景:先加后移可逆回到原字节
- **当** 对同一地址先应用 add、再应用 remove，其间条目集无其它净变更，且 overlay 由本路径写出
- **那么** overlay 的**字节内容必须**与 add 之前完全一致；若 overlay 曾被人工编辑，**只**保证条目集合等价

#### 场景:overlay 读失败时拒绝改写而非当空集
- **当** overlay 存在但读取失败（权限/IO），或其体积已超过 loader 上限
- **那么** 应用腿**必须**抛错、**禁止**写入；提案腿**必须**给出空提案（**禁止**提议一份应用腿会拒的变更）

#### 场景:写侧闸门拦住会导致整份失效的写入
- **当** 本次写入会使 overlay 越过 loader 上限，或单侧条目数超上限，或 `rules.yaml` 自身被命名为 `noise_senders.overlay`
- **那么** **必须**抛错、**禁止**写入

#### 场景:存量条目可被移除
- **当** overlay 里存在本能力生效前写入、不满足可加入判据的条目（`com`、`<a@x.com>`、`> 254` 字符的行）
- **那么** 对**其中任意一行** `l` 单独发起的 `{ remove: [l] }` **必须**被接受并真正删除它，**禁止**被任何批量闸（条目数 / 请求字节）拦下——哪怕这一行本身就超过 `MAX_REQUEST_BYTES`；而 `<a@x.com>` 这类匹配侧永不命中的串走 `add` 仍**必须**被拒

#### 场景:移出不撤销人工规则
- **当** 被移出的地址同时被人工 `rules.yaml` 的 `noise_senders` 命中
- **那么** 该地址**必须**仍被降噪（生效集是并集），文档**必须**明示人工规则要人工改

#### 场景:反馈路径绝不写 rules.yaml
- **当** 反馈闭环的任何路径（提案、应用，及两者的抛错路径）执行
- **那么** 人工维护的 `rules.yaml` **必须**逐字节不变
