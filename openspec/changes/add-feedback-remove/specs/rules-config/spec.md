## 新增需求

### 需求:noise overlay 的机器写入语义——canonical 归一、入口校验、集合运算与原子发布

`noise_senders.overlay` 是**机器文件**（loader 只读、一行一个发件人），其**唯一写者**是 `apply-feedback` 路径。该路径**禁止**写人工维护的 `rules.yaml`——两者的合并只发生在加载期（`noiseSenders = rules.yaml 项 ∪ overlay 项`）。

**canonical 归一**：每个条目在**写入前**必须归一为 `trim` → 去掉包裹的 `<>` → 转小写 → 丢弃空串，与 `rules.yaml` 列表项的既有 ingest 纪律一致（使并集/差集去重成立、且与只做小写归一的匹配侧对齐）。事件里回给上层的值**必须**已是这一形态——确认视图展示的即实际写入的。

**入口校验**：canonical 化后的条目**必须**是非空、长度 ≤254、**全部为可打印 ASCII** 的 `local@domain` 或 `domain`（域名 ≥2 段、每段以 `[a-z0-9]` 起止、段内可含 `-`）。不满足者**必须**响亮失败（抛错 → `run.failed`），**禁止**静默丢弃——静默丢弃会让用户以为加/移成功、实则名单没变。

**非 ASCII（IDN）条目必须拒绝**：匹配侧比对的是 normalizer 产出的 `fromEmail`（**只小写、不转 punycode**），故只在写入侧做 IDN 归一会写进一个**永不命中**的条目 = false-green（用户以为加了降噪、实际不生效）。支持 IDN 必须写入侧与匹配侧同时改，不在本能力范围。控制字符同路拒绝。

**来源分级**：上述 throw 只适用于**用户输入**（自然语言里点名的地址、确认后回传的结构化项）。**非用户输入**（DB 高频发件人候选、overlay 里的现有行）中校验不过的条目**必须**静默丢弃而非抛错——一条历史坏数据不应让整条命令失败。

**集合运算与发布**：一次应用求 `existing ∪ add \ remove`，经**同盘 tmp + rename** 一次性原子发布（**禁止**分两次写）。`added` = add 中不在现有集的，`already_present` = 已在的，`removed` = remove 中真在现有集的，`not_present` = 不在的。`added` 与 `removed` **皆空时禁止写文件**（重发 apply 连 mtime 都不动）。同一 input 内 add / remove 各自去重；同一地址同时出现在两侧**必须**抛错，**禁止**静默任选一边或互相抵消成无操作。

**可逆性**：条目集按 overlay 行序维护（新增追加在末尾、删除不扰动其余行序），故对同一地址**先 add 后 remove**，overlay 的**字节内容必须回到 add 之前**。

#### 场景:写入前 canonical 归一
- **当** 应用的条目为 `"  <FOO@Example.COM>  "`
- **那么** 回执里的条目与 overlay 里实际写入的行**必须**同为 `foo@example.com`（去空白、去 `<>`、小写）

#### 场景:非法条目响亮失败且不落盘
- **当** 用户入口收到空串、纯空白、含控制字符、`a@`、`@b.com`、`a@@b.com`、无点的裸串、超长串或非字符串
- **那么** **必须**抛错使 run 失败，且 overlay 的内容与 mtime **必须**均未变（校验先于任何写）

#### 场景:非 ASCII 域名拒绝而非单侧归一
- **当** 用户入口收到 `用户@例子.com` 这类含非 ASCII 的条目
- **那么** **必须**抛错并说明 v1 不支持 IDN；**禁止**归一为 punycode 写入 overlay（匹配侧不转 punycode，写入即 false-green）

#### 场景:历史坏行不阻断命令
- **当** overlay 里存在校验不过的历史行（手工编辑遗留）
- **那么** 该行在提案与归一时**必须**被静默跳过，其余条目正常处理，**禁止**因此使整条命令失败

#### 场景:集合运算一次原子发布
- **当** 一次应用同时含 add 与 remove
- **那么** **必须**求 `existing ∪ add \ remove` 后经 tmp+rename **一次**发布，回执四态各自反映真实变更

#### 场景:重发同一应用幂等且不写
- **当** 对同一组 add/remove 重发应用
- **那么** `added`/`removed` **必须**退化为空、对应条目落 `already_present`/`not_present`，且 overlay **必须**未被写（mtime 不变）

#### 场景:先加后移可逆回到原字节
- **当** 对同一地址先应用 add、再应用 remove
- **那么** overlay 的**字节内容必须**与 add 之前完全一致

#### 场景:反馈路径绝不写 rules.yaml
- **当** 反馈闭环的任何路径（提案、应用、拒绝）执行
- **那么** 人工维护的 `rules.yaml` **必须**逐字节不变
