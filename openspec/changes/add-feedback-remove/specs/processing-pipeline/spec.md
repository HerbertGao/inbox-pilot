## 新增需求

### 需求:降噪反馈两触发——提案腿干跑无写、应用腿幂等落盘，加入与移出共用同一条流

pilot **必须**认两个反馈触发，且**禁止**为撤销新增触发名（撤销是同一意图的反向）：

| trigger | input | emit | 写 |
|---|---|---|---|
| `interpret-feedback` | `{ text }`（既有 NL→add 路径）**或** `{ add?, remove? }`（结构化） | `interpretation.proposed { add: string[], remove: string[] }` | 无 |
| `apply-feedback` | `{ add?, remove? }` | `feedback.applied { added, already_present, removed, not_present }` | overlay 一次原子写 |

**pilot 禁止做自然语言意图解析。** 方向（加入 / 移出）与地址**必须**由调用方以结构化 JSON 给出；pilot 只做归一、校验、集合运算。理由：NL→结构化那层归调用方（命令框后接的 agent），而写在 pilot 里的中文分词/关键词/裸域名扫描**没有任何仓内机制会重跑**——它一旦漂移就是静默错判。既有 `{ text }` → add 路径**必须**保持行为不变（继续对每日摘要展示的高频发件人 TOP-N 做确定性子串匹配），本能力**只**新增结构化入口。

**未知触发名**仍**必须**抛错，**禁止**静默走轮询。

**emit 侧字段恒在**：两事件的**每个**声明字段**必须**恒出现，无变更即空数组，**禁止**省略——上层逐字段校验 `string[]`，缺一个即整条命令落契约不符。

**恰好 emit 一次**：每个命令 run **必须**恰好 emit 一次它的命令事件，且**一次性携带全部声明字段**。**禁止**分两次 emit（如 add 一个、remove 一个）——上层数同 kind 事件个数，≠1 即失败。

**input 侧两条规则方向相反，必须分开实现**：

- **缺 key 必须视作空数组、禁止抛错**：跨仓部署序是 pilot 先、view 后，那个窗口里旧 view 发的是只含 `add` 而无 `remove` 键的 input；把它当非法输入会让整个窗口的「加」全部失败。
- **key 存在但不是 `string[]` 必须抛错**：当空集处理会让「忽略畸形输入并回四个空桶」走成功路径。上层对畸形 input 会先返 400、不发起 run，但应用腿是**独立入口**（可绕过 UI 直调），故 pilot 侧也必须拦。

**提案就是将实际写入的 diff**：提案腿**必须**镜像应用腿的全部入口闸（条目数、序列化字节，含它们对本次请求第一条的豁免——见 `rules-config` 的「撤销可达性」），超预算时**截断**提案而非报错——干跑腿不能抛错，但也**禁止**提议一份应用腿必然拒绝的变更（用户确认后拿到失败，而契约里没有字段能解释原因）。

#### 场景:提案不得超出应用腿的接受范围
- **当** 结构化提案的条目数或写入后的字节数会越过应用腿的闸
- **那么** 提案**必须**被截断到应用腿一定会接受的前缀；把该提案**逐字**投给应用腿**必须**通过

**两腿的失败语义相反**：应用腿**必须**对非法项 / 非 canonical 项 / 同项冲突抛错；提案腿**绝不抛错**。归一与合法性规则见 `rules-config`。

**「绝不抛错」不限于非法项，它约束提案腿的每一处外部依赖**：非法项只是不出现在提案里；而它的两个外部触点——overlay 读与候选查询——的失败也**必须**被收住，各自退化为**空提案 + 一条只含 kind 的告警**。理由是上层的健康态由最近一次 run 派生：一次 DB 抖动或一次读不到文件，会把健康的服务画成监控墙上的翻车，而按数据最小化，抽屉里看不到原因。响亮失败由应用腿承担。

#### 场景:候选查询失败不使提案腿失败
- **当** `{ text }` 腿的高频发件人查询（本腿唯一的 DB 触点）抛错
- **那么** run **必须**正常结束、两字段皆为空数组，并留下一条**只含 kind**的告警（**禁止**记查询参数或任何发件人值）

**回执报的是「文件已改」，不是「已生效」**：overlay 由命令进程写，而规则快照在常驻服务启动时读取；**「移出」后需重启常驻服务才实际解静音**。该限制**必须**出现在面向操作者的文档与生产验收步骤里——否则本能力的用户可见目标在生产上不成立，而只验文件内容的验收会必然通过。

#### 场景:回执不蕴含已生效
- **当** 应用腿回执 `removed` 非空
- **那么** 文档与验收**必须**明示：该发件人的邮件在常驻服务重启前仍会被降噪；只验 overlay 内容的验收**禁止**被当作本能力生效的证据

#### 场景:提案阶段无任何写
- **当** `interpret-feedback` 完成
- **那么** run **必须**只 emit `interpretation.proposed`，overlay 与 `rules.yaml` 的内容与 mtime **必须**均未变

#### 场景:两事件字段恒在且恰好一次
- **当** 一次提案或应用没有解出/产生任何变更
- **那么** 事件里声明的字段**必须**全部出现且为空数组，该 kind **必须**恰好出现一次

#### 场景:结构化入口决定方向，pilot 不猜
- **当** input 为 `{ add: [...], remove: [...] }`
- **那么** pilot **必须**按调用方给定的方向分别求解，**禁止**从任何自然语言线索推断方向

#### 场景:既有 NL 路径的匹配集不变、结果为其合法子集
- **当** input 为 `{ text }`
- **那么** 匹配集**必须**与本能力变更前相同（仍为高频发件人 TOP-N 的确定性子串匹配），提案的 `add` 为该结果中**通过 `rules-config` 可加入判据的那些项**（`root@nas`、`admin@10.0.0.5` 这类匹配侧本来就命中、且不在豁免表内的候选**必须**进提案），`remove` 为空数组

#### 场景:`{ text }` 腿读 overlay，但禁止用它过滤提案
- **当** 用户点名的地址已在 overlay 里
- **那么** 它**必须**照常出现在提案的 `add` 里，「已在名单里」由应用腿的 `already_present` 桶如实回执。本腿读 overlay **只为**两件事：判定它可用（读失败即给空提案）与取字节基线（喂给与应用腿同一道的字节闸）；**禁止**据它过滤提案——按当前名单过滤会剔掉用户**点名的那个**（真阳性），只留下经短 token 松匹配进来的其余候选（假阳性），确认页因此展示的是用户没点过的地址

#### 场景:input 形态路由
- **当** input 带 `add` 或 `remove` 任一**自有**键（**禁止**取自原型链）
- **那么** 走结构化分支；两键皆无时走既有 `{ text }` 路径（`text` 缺失或非串时按空文本处理，emit 两个空数组）

#### 场景:键在但值为 undefined 属畸形
- **当** 应用腿收到 `{ add: undefined }`
- **那么** **必须**抛错（键存在即受「必须是 `string[]`」约束），**禁止**与「缺键」同等对待

#### 场景:缺 key 不失败、畸形 key 失败
- **当** 应用腿收到只含 `add` 而无 `remove` 键的 input
- **那么** **必须**正常应用；而当某个键存在但不是 `string[]`（如 `{add:"x"}`、`{add:[1]}`）时**必须**抛错

#### 场景:提案腿不因非法项失败
- **当** 提案腿收到含非法项或畸形 shape 的 input
- **那么** run **必须**正常结束、无任何写，相应项**必须**不出现在提案里

#### 场景:未知触发名响亮失败
- **当** 命令用了 pilot 不认识的触发名
- **那么** run **必须**以失败结束，**禁止**静默走轮询或伪装成功
