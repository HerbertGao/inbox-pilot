## 上下文

契约 SOT = hangar `add-view-feedback-remove` 的 `specs/hangar-view/spec.md`；域细节实施说明见同目录 `design.md`（冲突时以 spec.md 为准）。本文件只记 inbox 侧自己要裁决的点。

**该 SOT 目前没有版本锚**：hangar 侧那份提案尚未提交（工作区里是未 commit 状态），没有 commit / tag 可引。代价是本侧引用的事件形状（两字段 emit、四桶回执、跨桶不交）只由跨仓集成兑现，SOT 若在两仓之间漂移，本侧不会有任何自动信号——发现点是 view 判 `receipt_mismatch`。hangar 侧一旦提交，此处应补 commit。

## 决策

### ① pilot 不做自然语言意图解析（定型）

方向与地址由调用方（Pi / Claude Code / CLI）给结构化 JSON，pilot 只做归一、校验、集合运算。

**为什么不在 pilot 里做。** 曾有一版让 pilot 自己解析中文 NL（切句字符类 + remove 关键词集 + 裸域名扫描正则），整节删除。理由是它实测产出三条「少一个字符」级缺陷，而**没有任何仓内机制会重跑一份写在 markdown 里的正则**：

- 切句字符类里的全宽标点在文档往返中被折叠成 ASCII、顿号完全缺失 → 「把 a@x 降噪、把 b@y 移出」成了一句 → 两个地址全判 remove；
- 裸域名正则的 lookahead 少一个 `@` → `first.last@company.com` 额外抽出 `first.last`，写成用户从没点名过的域级降噪规则；
- remove 关键词是整句子串匹配、包含地址本身 → `restore@example.com` 因含 `restore` 被判反向。

本仓实测同源缺陷：`把noreply@taobao.com加进降噪`（中文不加空格是常态）整句被送进校验 → run.failed；`按 readme.md 说的把 taobao 加进降噪` → `readme.md` 被当显式项写进提案，且顺手关掉模糊匹配，用户真正想降噪的地址静默消失；`别再降噪 taobao 了`（意图＝移出）→ 提议**加入**。

命令框后面要接的 agent 本来就在做 NL→结构化，这层留在 pilot 里是重复且不可回归的。

### ② 两腿的失败语义相反

- **提案腿（干跑）对非法项不抛错**：非法项只是不出现在提案里；一项都没有时两侧皆 `[]`，确认页现成的空态文案就是回执。理由：hangar-view 的健康态由**最近一次 run** 派生，一次打错字的 `run.failed` 会把健康的 inbox 画成监控墙上的翻车，而抽屉按数据最小化看不到原因——用户输入错误不该污染 liveness 信号。
- **应用腿对非法项 / 非 canonical 项 / 同项冲突抛错**：到应用腿的项是刚给人看过的结构化结果，异常即契约漂移，该响亮。

这是对「非法输入 fail loud」的一处定向降级，fail-loud 由应用腿承担。

### ③ 应用腿拒绝非 canonical 项

归一化对合规输入是**幂等**的；不幂等说明调用方跳过了提案腿，是契约违规。这条把「确认页显示的 == 实际写入的」从纪律变成**结构保证**——而不是靠两个入口各自记得归一。

配套：**loader 与两腿共用同一个归一函数**（见决策 ⑩）。多份实现必然漂移，而 view 的回执校验按原串比较，漂移一个字符就让每条命令都报 `receipt_mismatch`。

### ④ 非 ASCII 域名 v1 直接拒绝，不做单侧归一

只归一写入侧会**静默不生效**：overlay 存 punycode，而匹配侧 `applySafetyRules` 比的是 `email.fromEmail`（normalizer 只小写、**不转 punycode**）→ 用户以为加了降噪、实际永不命中 = false-green。真要支持必须两侧同时改，并含存量 overlay 迁移（另开一条）。

实现上用「含任何码位 > U+007F 即非法」一条断言覆盖。控制字符同路拒绝，且**正则用码位转义写**——控制字符本身贴进源码或文档会在编辑器 / 剪贴板 / JSON 往返里被静默吃掉，一份「看起来有这个字符类」的正则会变成没有。本仓实测踩中两次，两次都是 `file(1)` 把源文件判成 `data` 才暴露。

### ⑤ 同项同时出现在 add 与 remove → 抛错

不静默任选一边：`(existing ∪ add) \ remove` 会让 remove 悄悄胜出，而回执 `{added:[X], removed:[X]}` 在读者眼里是「加了又移了」、文件里却没有 X——回执说谎，且 view 的跨桶检查会判它失败。提案腿则把该项从两侧同时剔除（它不抛错）。

### ⑥ 可加入判据取「匹配侧可达集 − 政策豁免」，而不是「只处理真正的邮箱」

**判据全文与豁免表住在 `rules-config` 规范，本节只记为什么这样裁。**

`matchNoiseCandidates` 的匹配集不变，其输出过一遍 `keepValidEntries`。**这一层的作用是过滤，不是归一**——候选来自 `repo.countRecentSenders`，其 `fromEmail` 已经 `normalizeFromAddress` 剥 `<>` + trim + 小写，归一维度上这层是恒等的。

初版把过滤判据定成「只处理真正的邮箱」：RFC dot-atom local + 域标签 ≤63 + ≥2 位纯字母 TLD。**它被推翻，因为它严于匹配侧。** 匹配侧是 `normalizeFromAddress` 的 `^[^\s<>@]+@[a-z0-9.-]+` 与 `matchesDomain` 的后缀比，两条都收无点域与数字 TLD——于是 `root@nas`、`admin@10.0.0.5` 这一整类（NAS、路由器、内网 cron、裸 IP）**在匹配侧本来就生效**，却被判为不可加入：提案腿静默丢弃、用户只看到空提案，而摘要表头正把这些发件人展示为可加入。对本能力生效前而言这是功能回归。

故**底座**两端锚定匹配侧的那两条谓词即得，恰是它们的不动点判定：宽于它会写进永不命中的条目（false-green，与 ④ 拒 IDN 同理），严于它会锁死真实存在的发件人。两个方向都是缺陷，底座只能取等。

**底座之上确实减了五格，不止裸 TLD 那一格**：非 ASCII local（`é@x.com` 匹配侧命中——`[^\s<>@]` 收每一个非 ASCII 字符）、控制字符 local、无点的纯域名条目、裸 TLD、前导 `mailto:`。①② 是内容侧的信任边界，与 ④ 的 IDN 裁决同源；③④ 是爆炸半径——一条域名条目静音整个后缀，与一个地址差一个量级；⑤ 是写路径的**不改写**纪律：`mailto:a@x.com` 匹配侧永不命中，而把它剥成 `a@x.com` 是替用户解析意图，本管道的契约禁止这么做——local part 真叫 `mailto` 的发件人会被改写成另一个地址、静音错的人。故让它撞在判据上，由调用方自己提交裸地址。

**长度上限（`> 254`）是第六处偏离，但不是第六项豁免**：它是写入侧的资源闸，匹配侧对 255 字符的地址照样命中，减不出来。故判据的形状是 **`(匹配侧可达集 \ 五项政策豁免) ∩ {长度 ≤ 254}`**，不是一个裸等式——性质测试按这个形状建模，写成等式会让这一处偏离要么被漏掉、要么被冒充成一条政策。

第三格的代价要认：它挡掉的不只是 `com`，还有 `nas` / `localhost` / `router`——**正是本节努力要收的那类内网主机，只不过是在主机名层面**。故「整机静音」这个形态本能力不提供，替代路径是按地址加（`root@nas`、`cron@nas`）。这是一笔明知的取舍，不是判据的疏漏。

### ⑧ 两个归一，对应两个问题；loader 的那一份与本能力生效前逐字节同语义

「一行是什么」与「用户指的是哪个条目」是两个问题，各一份实现（都住 loader 模块）。行归一**不剥 `<>`**——它与本能力生效前逐字节同语义，故存量 overlay 的生效集不迁移。用户输入归一剥到不动点。

曾把两者合成一个「剥 `<>`」的函数，代价是两条：① 存量惰性行 `<a@b.com>` 在重新部署后转活、开始静默已读，且**不需要任何写**、无回执无日志；② 只剥一层导致归一非幂等，一次无关的 apply 会把非不动点值写盘，下一次加载再剥一格——把一条从未被确认的规则推向生效。

### ⑨ 读的失败语义按方向分：loader fail-open，写路径 fail-closed

同一个「读不到 overlay」，两侧要相反的默认。loader 读不到 → 空集是对的（不静音，安全方向）。写路径读不到 → **绝不能**当空集：add 侧会全量覆盖抹掉整份名单并回绿；remove 侧会回执 `not_present`，而地址其实还在名单里、还在被静默已读——用户以为已撤销、不会重试，而这正是本变更存在的理由。故写路径只把 `ENOENT` 视为空集，其余一律抛错。

跨仓契约把这块明确委托给了本侧：view 的四桶校验**不是**「回执与磁盘一致」，后者只能由 pilot 侧 self-check 兑现。初稿把它记成「已知残留」，等于没接住这个委托。

### ⑦ 无实际变更时不写文件

`added` 与 `removed` 皆空 → 跳过 tmp+rename。重发 apply 连 mtime 都不动，「不在名单的 remove 不产生写」是字面成立的。

### ⑩ overlay 格式的所有权收进 loader 模块（本变更的结构决定）

前述 ⑧⑨ 是同一个病的两个症状。**根因是这份文件没有所有者**：关于它的五个语义问题——「一行是什么」「哪些条目可加入」「多大算超限」「这个文件是哪个」「键存在吗」——各被 loader / 提案腿 / 应用腿独立回答 2–3 次。

**成对一致不具传递性。** 三个持有者时，把 (A,B) 调平必然打破 (B,C)。所以「让某一份让步」的修法必然产出下一处分歧，而不是收敛。

故这五个答案各只留一份，住在 loader 模块（`canonicalizeOverlayLine` / `isAddableEntry` + `checkEntry` / `readOverlayFile` / `resolveNoiseOverlayPath` / `hasOwnKey`），`pipeline.ts` 降级为纯消费者。判定尺度随之从「测试守着一致性」变成**构造性事实**：

- **「这个文件是哪个」由派生回答**，不由比较回答：路径 = `dirname(RULES_FILE)/noise_senders.overlay`，一个旋钮定两个位置（⑫）。
- **撤销可达性**：loader 接受的任意一行 `l`，`{remove:[l]}` 恒被接受。它**按可达性陈述**，而不是从「共用前置里不含可加入分量」推出来——那个论证每加一道闸就要重来一次，且已被论错过两次；落法是闸只从第二条起生效。
- **方向差异只存在于一处**（`checkEntry` 的参数），结构上无法只改一半。
- **失败语义是参数而非第二份实现**：`readOverlayFile(path, 'fail-open' | 'fail-closed')`。loader 要 fail-open（读不到就不静音），写路径要 fail-closed（读不到不等于空集），两者都对，但共用同一份读与同一个尺寸量（`statSync().size`）。

**这条决策诊断对了病、开小了药。** 「五个问题各被回答 2–3 次」确是分歧之源，但把五个答案收给一个所有者，剩下的仍是五个问题——每个问题带着自己那一批状态，且每个状态要在两条腿上各表态一次。收尾是**少问三个**：见 ⑪。

### ⑪ 防御机器的减面裁决：换一套判据、删一套旋钮、保留一套机器

对抗 review 产出的新 blocker 有一个共同位置：**本能力新增的防御机器**，而不是「加个 remove 路径」本身要的东西（集合运算、四桶回执、写路径 fail-closed 读——这三样至今零 finding）。

机制是组合爆炸，不是修复质量：每加一道闸就多出一批状态（`readOverlayFile` 一家就要对 7 种文件系统情形表态 × 2 种失败语义），而**每个状态在提案腿与应用腿各要填一次且必须一致**。找空格的成本随这张表增长，补一格又长出新的一行一列。

三套机器的最终裁决（逐条的实现动作见 `tasks.md` §8）：

| 机器 | 防的是 | 裁决 |
|---|---|---|
| `isAddableEntry` 的 RFC 判据 | 写进永不命中的条目 | **判据换掉、函数保留**：改为「可达集 − 政策豁免」（⑥）。原判据严于匹配侧，把 `root@nas` 一整类判成功能回归 |
| overlay 路径旋钮 + 文件同一性判定 | operator 把 env 指到自己的 `rules.yaml` | **连旋钮一起删**：路径改为从 `RULES_FILE` 派生，同一性判定随之没有对象可判（⑫）。这是三套里唯一一套连问题都消掉的 |
| `fitWithinWriteBudget` | 提案里出现 apply 会拒的项 | **保留**。曾以「它不计 `present − remove` 的最终大小」为由删掉，该前提**是错的**：函数本来就先算 `kept = present − remove` 再定尺寸。删掉会让提案腿不再镜像应用腿的字节闸，与 `processing-pipeline` 规范正面冲突 |

`{text}` 腿的 **present 差分**是真该删的那一半：它剔掉用户点名的真阳性、只留短 token 松匹配进来的假阳性。该腿仍读 overlay，但只为可用性判定与字节基线。

**保留的判断**：写路径 fail-closed 读（⑨）承重——把「读不到」当空集会让一次 add 抹掉整份名单；tmp+rename 原子写与四桶回执成本已付且被跨仓契约要求；④ 拒 IDN 是 2 行且防的是真 false-green；`fitWithinWriteBudget` 见上。减面减的是防御面，不是这些。

### ⑫ 旋钮存废的尺子：设错了是响亮失败还是静默失败

本项目**刻意保持低可配置度**——它不该把自己呈现成一个高度可配的系统。一个旋钮该不该存在，只问一句：**它被设错时，是响亮失败还是静默失败？静默失败的旋钮不许存在。**

- **overlay 路径的独立 env 旋钮：删**。它指错的后果实测发生过——一次 apply 把 operator 的 `rules.yaml` 按平铺格式整体重写、缩进结构毁掉、无备份，而回执报的是成功。静默，故不许存在。路径改为**派生**：`dirname(RULES_FILE)/noise_senders.overlay`。一个旋钮定两个文件的位置，它们不可能被指到对方身上。
- **`RULES_FILE`：留**。它指错的后果是加载失败、全字段 carry-forward、一条告警——响亮，operator 看得见。

**「这两条路径是不是同一个文件」那一整套判定随旋钮一起删除，且不设任何替代机制**：既然撞不上，就没有对象可判。两条提案腿现在没有路径闸；应用腿只剩一次纯字符串比较（`resolve()` 两边取等），仅当 `rules.yaml` 自己就叫 `noise_senders.overlay` 时为真。它不落任何文件系统调用，故软链 / 硬链 / 大小写不敏感盘 / bind mount 这类别名机制在这里**没有作用面**——**禁止**以任何理由为它们重建一道闸。

## 可逆性的确切范围

overlay 的字节内容是「有序条目集」的**纯函数**（新增追加在末尾、删除不扰动其余行序），故条目集相同 ⇒ 字节相同。由此推出：对同一地址先 add 后 remove、**其间条目集无其它净变更**时，字节回到 add 之前。（不写成「先加后移必回原字节」——那句按字面可被 `add X → add Y → remove X` 证伪。）

**字节等价只对由 `writeNoiseOverlayAtomic` 写出的文件成立。** 人工编辑过的存量文件（无尾换行 / CRLF / 空行 / 重复行 / 大写）写回时按 canonical 形态重新序列化，**只保证集合等价**——self-check 对这两种情形各有一条断言。

## overlay-only：移出不是全局撤销

生效降噪集是 `rules.yaml noise_senders ∪ overlay`，本路径只动 overlay。同时被人工 `rules.yaml` 命中的地址「移出」后**仍会被降噪**；「不在名单」也只表示不在机器 overlay。规范里已写明**人工规则要人工改**。

## 已知残留（本变更不修，明确记账）

- **overlay 改动在常驻 daemon 内不立即生效**：`startRulesConfigReload` 全仓只有测试调用，生产 `buildAndPublish` 只在模块加载时跑一次；hangar daemon 长驻 + ESM 模块缓存 ⇒ **移出后需重启 daemon 才实际解静音**。属既有缺口（`rules-config` 规范的「改即生效」在生产未接线），修它要动 rules-config 的生命周期接线，越出本变更范围。
  **这条必须对用户可见**，否则本变更的用户可见目标在生产上不成立而全套验收仍会绿：已同步写入 `proposal.md` 的「行为变更（须知）」与 `tasks.md` 的生产验收步骤。
- **校验不过的历史 overlay 行仍被 loader 消费**：如一行 `com` 会让所有 `.com` 发件人命中降噪。本变更已让这类行**可经 remove 删除**（决策见 `rules-config` 的「两侧合规判据不同」），但 loader 仍会消费它们直到被删。让 loader 与写侧共用同一套合法性过滤属 loader 侧改动，另开一条。
- **跨进程并发写丢更新**：进程内 read-modify-write 全程同步、不可交错；跨进程无锁。tmp 文件名已带 pid（消除互踩与软链预置），但两个进程同时 apply 仍可能后写覆盖先写，而先写那次的回执是成功的。单容器部署下触发面 = 滚动重启窗口，概率低；真要闭合需锁文件或 CAS。

## 风险

- **行为变更**：应用腿对非法项与非 canonical 项从静默处理改为抛错。调用方必须先走提案腿。
- **部署序**：inbox 先、view 后。反序时**经 UI 的**路径在提案阶段即契约不符、此时无写；但应用腿是独立入口，绕过 UI 直调时旧 pilot 会照旧应用 add 半边而 view 仍判失败——即「报失败但写已发生」。故顺序卡死。
