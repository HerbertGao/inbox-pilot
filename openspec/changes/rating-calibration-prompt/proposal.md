## 为什么

线上实证（接入当天 1189 封旧邮件）：P0–P2 占 **93%**、仅 5.6% 进 P3 静默——分类器**系统性过度评级**，Telegram 推送与每日摘要过吵。根因在分类**源头**：prompt 对 P0/P4 口径过宽（「任何疑似…→P4」、P0 含「交易/告警」一刀切）。收紧 prompt 是**治本、零运维、最高杠杆**的一招。但 prompt 只是最佳努力约束，单向收紧有「反而放过真钓鱼」的安全回归风险，故必须配**双向回归语料**守门。

本 change 与并列的 `noise-discovery`（手动降噪轴，治尖峰）互补不重叠：此处治系统性高估的长尾，那里治固定少数发件人的尖峰。

## 变更内容

- **P4 口径收紧**：从「任何疑似钓鱼/诈骗/异常登录/支付风险 → P4」改为「P4 需**内容层欺骗证据**（诱导收件人按欺骗前提行动）」；**表层信号**（可疑 TLD / 截断 / 未渲染模板 / return-path 单独，尤其命中自有转发域）**不单独构成 P4**。
- **P0 去「交易/告警」一刀切**：交易收据类降至 P2；P0 收窄为真正需立即人工处理者。
- **各 P 级补反例 + 默认下沉**：拿不准往低判（宁可进摘要、不要推送）。
- **强制双向回归语料**：误报样例（网易登录 / PayPal 收据 / HKSS / 交易收据）+ 一组**真钓鱼**；守门目标「**真钓鱼掉出 P4 即失败**」，证明收紧没削弱检测。
- **BREAKING / 前置未解问题**：本仓 CI **无 `OPENROUTER_API_KEY`**、现有分类测试全注入假 `chatSpy`，**无法测真实 prompt 行为**。「CI 守门真钓鱼仍 P4」需真调模型 = 非确定 + 花钱 + 会 flaky。**验证机制是本 change 的前置未解问题**（选项见 design.md），spec 守门要求落地前必须先回答。

## 影响

- **代码**：`src/classifier/prompt.ts`（prompt 文案）；可能新增回归语料 fixtures 目录 + eval 运行脚本（机制待 design 定）。
- **文档同步**：`PROJECT_INIT.md §11`（prompt.ts 的权威原文源）**与 §5 优先级表**的 P0/P4 文案须随收紧同步，否则与代码漂移（CLAUDE.md 指 PROJECT_INIT 为完整需求权威）。
- **规范**：`openspec/specs/email-classification/spec.md`。
- **安全**：触及「P4/敏感不自动已读」边界的**上游**——靠四重拆弹守护：① 规则引擎硬底线原封不动（prompt 误评只能误判、清不掉底线）；② 真钓鱼反向语料 CI 守门；③ 非对称收紧（只收表层触发、内容欺骗仍偏 P4）；④ 现有 `confidence<0.65→P1` 兜底。
- **不改**：规则引擎 `applySafetyRules`、动作执行、规则配置。

## 非目标

- 不改规则引擎裁定逻辑（治本在 prompt 源头；强制硬底线仍在引擎）。
- 不做 `noise_senders` 手动降噪轴（那是并列的 `noise-discovery` change）。
- 不在本 change 内最终敲定 eval 基建实现——先定**机制方向**（见 design 未解问题），实现可拆后续。
- 不引入向量库 / 规则学习 / 多用户 / GUI。
