## 新增需求

### 需求:P0/P4 即时推送
`shouldNotifyNow` 为 true（即最终优先级 P0/P4）时通知器必须**尝试**推送（成功→对应 `notify` 动作记 `done`；单次 `executeActions` 调用内重试耗尽仍失败→记 `failed`；无渠道→记 `skipped`），**不保证一定送达**（at-most-once-after-retry，见 executeActions / processing-pipeline）；`shouldNotifyNow` 为 false 时**禁止**推送。

#### 场景:P0/P4 触发推送
- **当** 一封 `FinalDecision.shouldNotifyNow` 为 true 的邮件
- **那么** 通知器必须**尝试**经渠道推送通知——每次 `processEmail` 调用至多一条；推送可能因失败（`failed`）或无渠道（`skipped`）而未送达，不阻断 `markProcessed`；跨崩溃重跑为 at-least-once（≤1 次重复），与流水线 at-least-once 一致

#### 场景:非即时优先级不推送
- **当** 一封 `shouldNotifyNow` 为 false 的邮件（如 P1/P2/P3）
- **那么** 通知器必须不推送（其去向是摘要/计数，属后续阶段）

### 需求:通知不泄露完整正文
通知内容必须只包含必要字段——主题、发件人、原因、分类、置信度（P4 额外含风险标记与「不要点链接，请进官网核验」提示），**禁止**包含完整正文（`textBody`/`htmlBody`）。

#### 场景:P0 通知字段最小化
- **当** 推送一封 P0 邮件
- **那么** 通知必须含主题/发件人/原因/分类/置信度，且**禁止**含 `textBody`/`htmlBody` 完整正文

#### 场景:P4 风险提示
- **当** 推送一封 P4 风险邮件
- **那么** 通知必须含风险标记与「不要点链接，请进官网核验」类安全提示，且不含完整正文

### 需求:仅推送通知，绝不发送邮件
通知必须只发往聊天/推送渠道（telegram/bark 等），**禁止**触发任何邮件发送或回复（不可违反的硬约束）。

#### 场景:通知不触发邮件
- **当** 通知器推送任意通知
- **那么** 必须只调用聊天/推送渠道，禁止调用任何邮件发送 API

### 需求:渠道缺失时降级不崩
通知渠道未配置（如 `TELEGRAM_*` 缺失）时，通知器必须**降级为记日志并跳过**，禁止抛出未捕获异常或阻断处理流水线；降级时对应 `notify` 动作状态必须记为 `skipped`（区别于 `done`/`failed`）并含原因。

#### 场景:无渠道配置时降级
- **当** 需要推送但没有任何渠道凭据
- **那么** 通知器必须记一条结构化日志并跳过推送，不抛异常、不阻断 `processEmail`，且对应 `notify` 动作记为 `skipped`

### 需求:通知密钥只从配置读、不入日志
通知渠道凭据（本期 `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`）必须只从 P0 `config`（环境变量）读取，**禁止**写死在代码中；推送失败的日志**禁止**写入渠道凭据或邮件完整正文。

#### 场景:失败日志不泄露凭据与正文
- **当** 推送失败需记日志
- **那么** 日志必须只含结构化字段（如 kind/status/优先级），禁止含渠道凭据或完整正文
